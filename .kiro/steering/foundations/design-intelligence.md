# Design Intelligence Foundation

## Purpose

This foundation provides the reasoning layer above Design Principles, Usability Heuristics, and Gestalt Principles. It enables design judgment beyond rule checking.

## Position in the Knowledge Stack

```text
Governance
↑ Pattern Recommendation
↑ Design Reasoning
↑ Design Critique
↑ Usability Heuristics
↑ Design Principles
```

## Core Principle

Good design is not merely correct. It is understandable, usable, accessible, appropriate, scalable, and intentional. A design can pass every heuristic and still be weak. Design Intelligence evaluates quality beyond compliance.

## Evaluation Process

Always evaluate in this order:

1. **Goal** — Why does this exist? What outcome should it create?
2. **User** — Who is using this? What do they already know?
3. **Context** — Where is this used? Under what conditions?
4. **Constraints** — What cannot change? What must be preserved?
5. **Principles Review** — hierarchy, consistency, simplicity, affordance, feedback, visual balance
6. **Heuristics Review** — visibility, user control, consistency, error prevention, recognition over recall, accessibility
7. **Design Critique** — Focus, Hierarchy, Density, Rhythm, Clarity, Trust, Cohesion, Visual Noise, Attention Competition

## Design Reasoning

- **Appropriateness** — Is this suitable for the user, context, and business goal?
- **Complexity** — Is complexity justified? Can it be reduced?
- **Trade-Offs** — What is gained? What is lost? What alternatives exist?
- **Emotional Fit** — Does the response match the desired experience? (calm, technical, playful, premium, efficient, trustworthy)
- **Confidence** — Does the interface inspire trust?

## Aesthetic Reasoning

- **Visual Tone** — editorial, technical, premium, playful, minimal, enterprise
- **Visual Energy** — quiet, balanced, dynamic, expressive
- **Density** — sparse, comfortable, compact, dense
- **Structure** — strict grid, modular, asymmetrical, organic

## Pattern Recommendation

Process: Problem → Pattern → Component → Token

## Governance Review

Can this be reused? Can this scale? Can this be documented? Can this be automated? Can this become a component, token, or guidance?

## Design System Lens

Would this decision still make sense if repeated 100 times? If not, investigate a more systematic solution.

## Output Format

Observations → Assumptions → Strengths → Weaknesses → Trade-Offs → Recommendations → System Impact

## Agent Rule

Never jump directly to UI recommendations. Always reason through: Goal → User → Context → Constraints → Principles → Heuristics → Critique → Reasoning → Patterns → Governance.
